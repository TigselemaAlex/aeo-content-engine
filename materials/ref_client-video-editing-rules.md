# Edit Spec: Client Video Editing Rules


An Edit Spec is one page per client that turns their references and feedback into exact editing rules, so nobody has to guess what the client wants. Think of it as the client's recipe: the editor follows it, the CM checks against it, and every new client comment gets added to it.

## How it works

**The problem it solves.** Today the client sends a reference clip or a comment, the CM forwards a screenshot, and the editor interprets it. Each round the interpretation drifts, so the client repeats the same comment ("the logo needs to be scaled") and loses trust. The Edit Spec replaces interpretation with rules: not "make it like their clip" but "logo top right, 12% of frame width, visible the whole video".

1. **Collect the references.** The CM gathers what the client already publishes or likes: their own edited clips, a competitor that performs, any clip they sent us. Minimum 2, ideal 3.
2. **Break them down into rules.** In the Monday CM and Content Engine meeting, watch the references together and fill the template below, section by section. Write what you see, with numbers: seconds, sizes, positions, fonts.
3. **Build one pilot.** The editor makes ONE piece following the spec. No batch yet.
4. **Check before sending.** Editor and CM each run the QC checklist. If any rule in the spec is not met, the piece does not go out.
5. **Feed the spec.** When the client comments, the CM translates the comment into a rule and adds it to the Change log. Golden rule: the client never has to give us the same comment twice.

**Where it lives.** One copy per client, inside the client's folder, linked in the client's cohort thread. The CM owns it. The editor reads it before every edit.

## Baseline rules (all clients)

These rules apply to every piece, for every client, before any client rule is added. They come from our YouTube Optimization Framework. The client spec sits on top of this baseline: if a client rule says something different, the client rule wins and the reason goes in that client's Change log.

### Short form (Shorts, Reels, TikTok)

| Area | Baseline rule |
| --- | --- |
| Format | Vertical 9:16, under 60 s |
| Hook (first 1 to 3 s) | No intro, no greeting, no logo animation. Open with the question or the most surprising line. Style the key word of the hook differently (bold, bigger or accent color) so the viewer knows what the video is about at first glance |
| Pacing | A cut every 2 to 3 s. No visual mode (talking head, B roll, text card) lasts more than 15 to 20 s without a switch |
| Silences and cuts | Remove every pause over 0.5 s that is not there for emphasis. Use J cuts: the audio of the next clip starts 3 to 5 frames before the visual cut, so cuts feel natural |
| Captions | Always on, because most people watch muted. Sans serif font, lower third, one line, short phrases, one entrance animation (pop up fade in), no exit animation. Nothing hidden by the platform buttons |
| B roll | Cut to B roll at the moment a concept is introduced and match it to the spoken word. Darken and desaturate B roll when there is text over it |
| Zooms | Subtle zoom in (100 to 115%), ease in and ease out, 1 to 2 s each. Never aggressive |
| Story structure | Hook, foreshadow the answer, tension ("but" or "then"), answer, CTA |
| Music and sound | Music bed that matches the tone. 2 to 3 sound effects per minute at most, one per transition or emphasized word |
| CTA | Every Short points to a long form video ("full video in the comments"). A Short without a long form destination is a wasted viewer |

### Long form (YouTube, 5 to 15 min talking head)

| Area | Baseline rule |
| --- | --- |
| Format | Horizontal 16:9 |
| Hook (0 to 30 s) | Answer first. State the question and tease the answer within the first 10 s (35% of viewers leave in the first 10 s if the hook fails). No story openers, no long intro |
| Promise (30 to 60 s) | A clear line of what the viewer will get: "By the end of this video you will know X" |
| Pacing | Not the Shorts pace. A visual change (B roll, text overlay or cutaway) every 15 to 25 s. Longer holds are fine when the message carries itself |
| Filler and imperfections | Remove um, uh, like. Keep natural pauses used for emphasis and small imperfections, they make the speaker feel human. Jump cuts between sentences, never in the middle of a word |
| Pattern interrupts | Every 2 to 3 min, plus a "here is what is coming next" bridge before each new section |
| B roll | Cut to B roll when a concept is introduced, as a break from dense talking. Ken Burns style zoom on photos, screenshots and documents |
| Text overlays | Key stats, names, terms and dollar figures always appear on screen |
| Transitions | Simple fades or light zooms only. No flashy transitions |
| Close | Recap of 3 to 5 takeaways in the last 60 s, then one single CTA in the last 15 s. End screen pointing to the next video |
| Chapters | 5 to 8 chapters, the first at 00:00, each at least 10 s long, titles under 40 characters written as curiosity hooks, not "Introduction" |
| Captions file | Upload a custom SRT file, not auto captions. It helps YouTube and AI search find the exact segment that answers a question |
| Thumbnail (if we deliver it) | One focal point, a face with a clear emotion, 3 to 5 words max, high contrast. Must still read when shrunk to a tiny size |

## Pre-send QC checklist

Nothing reaches a client until both passes are done. If one box fails, the piece goes back to the editor with the failed item named.

**Pass 1: Editor, before handing to the CM**

- [ ] Watched the exported file (not the timeline) start to finish
- [ ] Baseline rules for the format (short or long form) are met, unless the client spec overrides them
- [ ] File opens and plays to the end, nothing cut, frozen or shifted
- [ ] Export settings match the spec exactly (ratio, resolution, fps, audio level, file name)
- [ ] Logo size and position match the spec
- [ ] Captions: no typos, no words hidden by platform buttons, synced with the voice
- [ ] Fonts and colors are the client's, not defaults
- [ ] Hook lands in the first 3 seconds
- [ ] Pacing rule met, no dead air or long static frames
- [ ] Every rule in the Change log is applied
- [ ] Nothing from the Never do row appears

**Pass 2: CM, before sending to the client**

- [ ] Watched it on a phone, with sound, start to finish
- [ ] Put it side by side with the client's reference: would the client see them as the same style?
- [ ] Checked each point of the client's last feedback, one by one, against the new version
- [ ] Would I publish this on my own account today? If not, it goes back
- [ ] Wrote the changelog for the client: "You asked for X, we did Y"

If the piece is a pilot, it goes out alone, with a clear ask: approve this style or tell us what to change. The batch starts only after approval.
